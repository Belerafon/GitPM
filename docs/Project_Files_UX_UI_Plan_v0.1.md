# UX/UI-план файлов проекта v0.1

Статус: предложение на согласование с владельцем продукта. Документ описывает только
пользовательский опыт; контракт репозитория и пошаговый технический план будут подготовлены после
одобрения.

## 1. Назначение и границы

У каждого Project появляется простое пользовательское файлохранилище для договоров, технических
заданий, таблиц, презентаций, сканов, изображений и других рабочих материалов. Оно не заменяет
существующий технический файловый менеджер рабочей копии:

- пользовательское хранилище показывает только файлы текущего Project;
- технический менеджер остаётся низкоуровневым инструментом для произвольной работы с файловой
  системой;
- оригиналы файлов входят в Git-репозиторий и участвуют в обычном процессе черновика, просмотра
  изменений, коммита и публикации;
- расширение файла не используется как список разрешённых типов;
- файл можно хранить, даже если GitPM не умеет показать его содержимое в браузере.

В первой версии хранилище плоское, без создания папок через пользовательский интерфейс. Это
сохраняет однозначность имён и ссылок. Файлы, помещённые техническим менеджером непосредственно в
канонический каталог файлов Project, появляются в пользовательском хранилище после обновления.
Вложенные каталоги до появления отдельного UX остаются зоной технического менеджера.

## 2. Точка входа на странице проекта

Рядом с описанием Project или сразу под ним, перед метаданными проекта, размещается вторичная
кнопка `Файлы`. Она должна восприниматься как часть информационного блока проекта, а не смешиваться
с кнопками редактирования, создания этапа и задачи.

Кнопка содержит:

- пиктограмму скрепки или файловой библиотеки;
- надпись `Файлы`;
- компактный счётчик, включая `0` для пустого хранилища.

Кнопка доступна также в архивном Project и для пользователей только с правом чтения: просмотр и
скачивание остаются полезными. Операции изменения внутри хранилища подчиняются текущему состоянию
черновика, режима записи (writer mode) и роли пользователя.

```text
Project P-26-ABC123
Редизайн личного кабинета заказчика
Заменить устаревший кабинет партнёра.

[ скрепка  Файлы  12 ]

Статус: Активен   Владелец: Анна   Начало: 01.09.2026   Срок: 15.12.2026
```

После успешной загрузки или удаления счётчик обновляется сразу, а при следующем обновлении рабочей
области сверяется с фактическим содержимым репозитория.

## 3. Правая панель файлов

Нажатие `Файлы` открывает отдельную панель справа поверх текущего контекста Project. Перехода на
другую страницу не происходит, выбранная Task не сбрасывается. После закрытия пользователь
возвращается точно в прежний контекст.

Просмотр самого содержимого — в отдельном окне браузера. В этой панели находится только список
файлов.

Состояние библиотеки:

```text
+----------------------------------------------------------------+
| Файлы проекта                                      12       ×   |
| [Поиск по имени...]          Сортировка: Имя    [Загрузить]    |
|                                                                |
|  [PDF]       [DOCX]      [XLSX]      [IMG]      [ФАЙЛ]        |
|  Договор     ТЗ_v3       Смета       Схема      Архив          |
|  2026.pdf    .docx       .xlsx       .png       .zip           |
|                                                                |
| Перетащите сюда файлы для загрузки                             |
+----------------------------------------------------------------+
```

По умолчанию используется похожая на Проводник Windows сетка плиток: крупная пиктограмма, под ней
имя файла. Вид можно переключать с сетки на табличный. Выбор пользователя сохраняется в cookie и
применяется к файловым хранилищам всех Project. Длинное имя переносится максимум на две строки;
полное имя доступно в подсказке и как доступное имя элемента.

Достаточно узнаваемых семейств пиктограмм:

- PDF;
- Word и совместимые текстовые документы;
- Excel и табличные форматы, включая CSV;
- PowerPoint и презентации;
- изображения с безопасной миниатюрой, если она доступна;
- текст, Markdown и исходный код;
- архивы;
- нейтральная пиктограмма для остальных файлов.

В панели инструментов находятся кнопки `Загрузить файлы`, `Переименовать`, `Удалить`, `Свойства`
и `Скачать`. Перетаскивание файлов в панель выполняет ту же операцию загрузки. После открытия файла
и возврата сохраняются запрос поиска, сортировка и позиция прокрутки.

## 4. Просмотр файла

Одинарный клик по плитке открывает файл в новой вкладке, если его безопасно отдать для встроенного
просмотра. Браузер сам показывает поддерживаемое содержимое. Для остальных форматов GitPM сразу
предлагает скачивание.

## 5. Операции с файлами

### Загрузка

Кнопка `Загрузить файлы` поддерживает множественный выбор. Панель показывает очередь, прогресс и
результат отдельно для каждого файла. По окончании загрузки панель не закрывается.

Если имя уже существует, GitPM ничего не перезаписывает молча. Диалог предлагает:

- `Заменить текущий файл` — сохранить прежнее имя и ссылки, создав новую версию в Git;
- `Загрузить под другим именем` — отредактировать предложенное имя;
- `Отмена`.

Разрешены Unicode и пробелы. Следует поддержать обычные допустимые имена Windows, чтобы
пользователю не приходилось переименовывать файлы перед загрузкой. Разделители пути,
зарезервированные имена и другие недопустимые для файловой системы варианты отклоняются с
конкретным пояснением рядом с полем. Внутри одного Project имена сравниваются без учёта регистра и
должны быть уникальными, чтобы репозиторий одинаково работал в Windows и в системах с
чувствительной к регистру файловой системой.

### Файлы больше 50 МБ

Порог 50 МБ является границей предупреждения, а не запретом. Для файла больше порога до начала
передачи открывается отдельное подтверждение:

1. Показать точное имя и отформатированный размер.
2. Объяснить, что оригинал и последующие версии остаются в истории Git, увеличивая время
   клонирования, получения изменений и занимаемое репозиторием место.
3. Потребовать ввести точное имя файла с учётом регистра, чтобы подтвердить намерение загрузки.
4. Активировать кнопку `Всё равно загрузить большой файл` только при полном совпадении имени.

Несколько больших файлов подтверждаются отдельно, чтобы одним введённым именем нельзя было
разрешить посторонний пакет. Во время передачи видны прогресс и доступная отмена. Ограничения
Git-сервера или транспорта могут привести к отдельной понятной ошибке, но GitPM не должен выдавать
предупреждение на 50 МБ за жёсткий лимит.

Отдельная операция позволяет заменить файл новым с другим именем и одновременно обновить ссылки.
Например, при замене `ТЗ_v1.docx` на `ТЗ_v2.docx` все ссылки в Task должны получить новое имя.

### Переименование

Открывается небольшой отдельный диалог. Текущее имя выделено, расширение остаётся видимым.
Изменение расширения вызывает неблокирующее предупреждение о возможном изменении предпросмотра.
Конфликт имени и недопустимое имя обнаруживаются до изменения репозитория.

Ссылки используют имя файла. Поэтому штатное переименование должно в одной операции изменить имя
и обновить все ссылки текущего Project. При ошибке вся операция откатывается.

### Удаление

Для файла без ссылок используется обычное подтверждение с его именем. Если ссылки существуют,
диалог показывает их количество и короткий список Task и комментариев, где используется файл.
Явное действие называется `Удалить файл и отвязать N ссылок`; при отвязке видимое имя сохраняется
в тексте как обычный текст, окружающая фраза не удаляется.

Удаляется файл из текущей версии репозитория. Диалог объясняет, что ранее закоммиченное содержимое
может сохраниться в истории Git. Интерфейс не должен обещать безопасное физическое уничтожение.

### Свойства

Свойства показываются компактной панелью с копируемыми значениями:

- имя и определённый формат;
- человекочитаемый размер и точное число байтов;
- канонический путь относительно репозитория, например
  `projects/P-26-ABC123/files/ТЗ_v3.docx`;
- даты создания, изменения;
- количество ссылок внутри Project;
- доступность предпросмотра.

Название даты должно соответствовать её реальному источнику. Время создания файла в конкретной
рабочей копии нельзя выдавать за устойчивую дату создания. Если это возможно без отдельного
реестра, файлу выставляется дата изменения, которую передал браузер из файловой системы
пользователя.

## 6. Ссылки на файлы в тексте Project

Символ `@` остаётся за людьми. Для файлов используется wiki-синтаксис, не зависящий от языка
интерфейса:

```text
Согласно пункту 5.2 [[file:ТЗ_v3.docx]], срок приёмки составляет 10 дней.
```

После ввода `[[` в Markdown-редакторе с контекстом Project появляется список файлов с
пиктограммой, именем и размером. Кнопка со скрепкой рядом с редактором открывает тот же выбор для
пользователей, которые не знают синтаксис. Выбранная ссылка вставляется в позицию курсора. Поиск
не учитывает регистр и находит любую часть имени.

Ссылка хранится по имени из примера выше. Одинаковые имена в пользовательском хранилище запрещены,
поэтому разрешение ссылки однозначно. Штатная операция переименования или замены новым файлом
обновляет такие ссылки атомарно.

В отрисованном тексте ссылка выглядит как компактная ссылка-файл с пиктограммой типа и именем.
Клик открывает файл в новой вкладке или начинает скачивание по тем же правилам, что клик в панели.
Отсутствующая ссылка отображается явным предупреждающим элементом с объяснением, а не неработающей
обычной ссылкой и не молча изменённым текстом.

Поддержка распространяется на Markdown-поля с однозначным контекстом Project, первоначально:

- описание Project;
- описание Milestone;
- описание и критерии приёмки Task;
- комментарии Task;
- заметки о трудозатратах, привязанные к Project и Task.

Глобальные сущности и текст без контекста Project не могут использовать неявные ссылки на файлы
проекта. Межпроектные ссылки не входят в первую версию и не должны молча расширять область Project.

## 7. Черновик, Git и внешние изменения

Загрузка, замена, переименование и удаление являются обычными мутациями черновика и подчиняются
оптимистичной версии (fingerprint) и режиму записи (writer mode).

Экран изменений группирует файлы под их Project и использует понятные подписи: `Файл добавлен`,
`Файл заменён`, `Файл переименован`, `Файл удалён` — для бинарных файлов. Для текстовых показывается
Git diff.

Пользовательское хранилище читает реальный канонический каталог Project. Обычный файл, добавленный,
переименованный или заменённый через технический менеджер, появляется после обновления. Если
внешняя операция создаёт неоднозначное имя, неподдерживаемую вложенность или несогласованные
метаданные, интерфейс показывает исправимое предупреждение, а не угадывает и не скрывает состояние
репозитория.


Отдельной базы данных или реестра для списка файлов, дат создания или авторов в GitPM быть не
должно. Если для возможности потребуются такие скрытые метаданные, от возможности следует
отказаться. Источник истины — файлы в папке Project «как есть».

## 8. Пошаговый технический план реализации

План намеренно разбит на небольшие законченные этапы. Каждый этап выполняется в отдельном рабочем
контексте, заканчивается тематическими тестами, проверкой diff и отдельным коммитом. Следующий этап
начинается только с чистого рабочего дерева. Если по фактическим зависимостям этап окажется слишком
большим, его следует разделить по границе server/web, не объединяя соседние этапы.

### Базовые технические решения

- Каноническое хранилище — обычные файлы в `projects/<project-id>/files/`. Никаких manifest,
  sidecar-файлов, отдельных YAML-сущностей или базы данных со списком файлов не создаётся.
- Имя файла является его идентификатором. Это отменяет ранее предложенный скрытый постоянный ID:
  без отдельного реестра связать такой ID с текущим именем невозможно. Штатное переименование или
  замена с новым именем должны атомарно переписывать ссылки `[[file:...]]` во всём Project.
  Внешнее переименование через технический менеджер может оставить явно показанную сломанную
  ссылку.
- Git не хранит время создания и изменения файла. Поэтому GitPM не сохраняет эти даты отдельно:
  показывает доступные даты текущей рабочей копии и вычисляемые даты Git с точной подписью
  источника. При загрузке можно передать `lastModified` браузера и выставить mtime рабочей копии,
  но нельзя обещать его сохранение после нового checkout.
- Хранить можно любой обычный файл. Для открытия сервер отдаёт безопасный MIME и
  `Content-Disposition: inline` только форматам, которые допустимо показывать в браузере; для
  остальных используется скачивание. Таким образом браузер сам показывает поддерживаемые PDF,
  изображения и текст, но GitPM не исполняет активное содержимое.
- 50 МБ — только порог осознанного подтверждения. Передача должна быть потоковой, без base64.
  Возможный эксплуатационный лимит сервера настраивается отдельно и возвращает понятную ошибку,
  но не маскируется под ограничение в 50 МБ.

### Этапы

| № | Законченный кусок | Проверяемый результат |
| --- | --- | --- |
| 1 | Закрепить формат каталога и правила валидации | Репозиторий принимает плоский каталог `files` внутри Project, обычные файлы любых расширений и Windows-совместимые имена; считает их непрозрачным содержимым, а не domain YAML; отклоняет symlink, вложенные каталоги, обход пути и конфликт имён без учёта регистра. Обновлены нормативные документы и тесты repository/validation. |
| 2 | Сделать read-only слой файлов Project | Domain/server умеют посчитать файлы, вернуть список, размер и доступные свойства, а также безопасно открыть или скачать один файл. Все пути жёстко ограничены текущим Project. Покрыты MIME, Unicode, пустой каталог, отсутствующий файл и hostile paths. |
| 3 | Сделать потоковую загрузку на сервере | Загрузка и замена содержимого работают через UI writer mode и fingerprint, не используют base64, не перезаписывают файл молча и откатываются при ошибке полной проверки репозитория. Сервер проверяет подтверждение файлов больше 50 МБ и возвращает стабильные коды конфликтов. |
| 4 | Сделать переименование и удаление на сервере | Обе операции соблюдают Project scope, fingerprint, защиту от symlink и конфликтов регистра. Пока ссылок ещё нет, API уже имеет явные режимы для будущей проверки и отвязывания ссылок. |
| 5 | Добавить кнопку и базовую правую панель | На странице Project видны `Файлы` и счётчик. Панель показывает пустое, загрузочное и ошибочное состояния, плитки с иконками и табличный вид. Выбор вида хранится в cookie пользователя и применяется ко всем Project. Этот этап пока только читает файлы. |
| 6 | Подключить пользовательскую загрузку | Работают выбор нескольких файлов, drag-and-drop, очередь и прогресс. Конфликт имени предлагает заменить или выбрать другое имя. Для каждого файла больше 50 МБ требуется точный ввод имени. |
| 7 | Подключить обычные действия с файлом | Выбор файла открывает новую вкладку либо скачивание согласно ответу сервера. Из панели работают скачать, свойства, переименовать и удалить. Свойства показывают только реально доступные файловые и Git-данные с указанием источника. |
| 8 | Ввести общий синтаксис файловых ссылок | Общий parser и domain-поиск распознают `[[file:имя]]`, находят все использования только в текущем Project и явно различают существующие и сломанные ссылки. Покрыты Unicode, экранирование, вредоносный ввод и запрет межпроектного расширения области. |
| 9 | Подключить ссылки к основным описаниям | Общий безопасный renderer, подсказки после `[[` и кнопка-скрепка работают в описаниях Project, Milestone и Task, а также в критериях приёмки. Клик использует тот же open/download маршрут, что файловая панель. |
| 10 | Подключить ссылки к комментариям и трудозатратам | Ссылки работают в комментариях Task и заметках о трудозатратах. Общий компонент сохраняет существующие упоминания людей через `@`; отдельно проверены создание, редактирование и отображение старых записей. |
| 11 | Сделать операции с учётом ссылок | Переименование и «заменить новым файлом» атомарно обновляют все ссылки текущего Project. Удаление показывает места использования и требует явного отвязывания; при отвязке подпись остаётся обычным текстом. Любая ошибка возвращает и файл, и тексты в исходное состояние. |
| 12 | Встроить файлы в Changes и завершить сквозные сценарии | Бинарные изменения получают понятную семантику добавления/замены/переименования/удаления, текстовые файлы сохраняют Git diff. Проверены direct/worktree режимы, технический менеджер, внешние изменения, read-only состояния, адаптивность и основные browser E2E-сценарии. |

### Границы проверки этапов

- Этапы 1 и 8: как минимум `verify:repository`, с дополнительными профилями реальных потребителей.
- Этапы 2–4: `verify:server`; при изменении drafts/security также `verify:workflow`, при изменении
  общих контрактов также `verify:repository`.
- Этапы 5–7, 9 и 10: `verify:web` плюс соответствующий server-профиль при изменении HTTP-контракта.
- Этапы 11 и 12: затронутые repository/server/web/workflow профили и сквозные
  `verify:e2e-ui`/`verify:e2e-workflow` по фактической границе поведения.
- Полный `verify:local` нужен только если реализация затронет корневую конфигурацию или влияние
  конкретного этапа нельзя будет уверенно ограничить.

Перед началом каждого этапа следует повторно посмотреть фактические изменённые импорты и уточнить
профили проверки. Этот список задаёт минимальную ожидаемую границу, а не разрешение пропускать
затронутые тесты.

## 9. Статус реализации

### Этап 1 — завершён

Реализовано:

- полное repository validation допускает опциональный плоский каталог
  `projects/<project-id>/files/` и не передаёт его содержимое domain YAML parser;
- обычные файлы с любым расширением, без расширения, с пробелами и Unicode считаются непрозрачным
  содержимым и не меняют количество доменных документов;
- введена общая проверка одного файлового имени на переносимый Windows-совместимый набор правил и
  регистронезависимый ключ сравнения;
- validation отклоняет недопустимое имя, конфликт имён без учёта регистра, вложенный каталог,
  symbolic link и специальный filesystem entry; обход пути исключён требованием одного валидного
  сегмента имени;
- нормативные Repository Format и Implementation Plan дополнены каноническим layout, правилами
  имени и стабильными кодами ошибок;
- добавлены unit-тесты правил имени и repository-тесты для бинарного содержимого, ложного `.yaml`,
  Unicode, файлов без расширения, вложенности, symlink и конфликта регистра.

Фактически выполненные проверки:

- первоначальный `corepack pnpm --filter @gitpm/validation typecheck` не запустился: в новом
  worktree ещё отсутствовал `node_modules` и команда `tsc` не была доступна;
- `corepack pnpm install --frozen-lockfile` — успешно;
- первый узкий запуск Vitest после установки зависимостей не загрузил `@gitpm/calendar`, потому
  что workspace dependency closure ещё не была собрана;
- `corepack pnpm --filter @gitpm/validation... build` — успешно;
- `corepack pnpm exec vitest run packages/validation/src/project-files.test.ts packages/validation/src/index.test.ts`
  — успешно: 56 тестов пройдено, один платформенный тест пропущен;
- первый запуск `corepack pnpm verify:repository` остановлен внешним лимитом команды через 124
  секунды до результата (`exit 124`), не из-за ошибки проверки;
- повторный `corepack pnpm verify:repository` с увеличенным лимитом — успешно: frozen install,
  сборка affected packages, lint, 117 repository-тестов, schema contracts и diff whitespace

Ограничения этапа:

- на Windows невозможно создать в одном каталоге два файла, отличающихся только регистром,

  общий регистронезависимый ключ отдельно покрыт и работает на Windows;
- этап намеренно не предоставляет список, свойства, чтение или скачивание файлов — это граница
  этапа 2; текущий `discoverRepositoryFiles` сохраняет контракт списка только domain YAML.
