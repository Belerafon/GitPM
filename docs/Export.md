# Экспорт данных

GitPM формирует экспорт из текущего снимка выбранной рабочей копии. Операция доступна
в верхней панели веб-интерфейса, через HTTP и команду `gitpm export`. Экспорт не изменяет
repository state и доступен ролям с правом чтения.

PDF, HTML, CSV и XLSX получают одну подготовленную модель `ExportReportModel`. Расчёты
расписания, трудозатрат, загрузки и отпусков берутся из общих пакетов, а не читаются
рендерерами из YAML самостоятельно.

## Имена файлов и снимок

Базовое имя имеет вид `gitpm-YYYYMMDD-<short-hash>`, где дата и первые восемь символов
берутся из `HEAD`-коммита:

- `gitpm-20260725-deadbeef-portfolio.pdf`;
- `gitpm-20260725-deadbeef-static.html`;
- `gitpm-20260725-deadbeef-csv.zip`;
- `gitpm-20260725-deadbeef-reports.xlsx`;
- `gitpm-20260725-deadbeef-repository.zip`;
- `gitpm-20260725-deadbeef-repository-with-git.zip`.

В отрисованные форматы попадает текущее содержимое рабочей копии, включая
незакоммиченные изменения. Хеш в имени фиксирует базовый `HEAD`, а не утверждает,
что рабочая копия чистая.

## Форматы

### PDF

По умолчанию включены разделы «Проекты» и «Люди». Дополнительно можно выбрать:

- план проекта с иерархией задач, статусами, исполнителями и зависимостями;
- Гант с фактическими сегментами времени;
- план-факт по задачам, людям, категориям и датам;
- загрузку команды;
- отпуска и отсутствия;
- профили сотрудников;
- аудит архивных сущностей, аннулированных TimeEntry, комментариев и истории коммитов.

Сводные страницы повторяют состав данных стандартных web-реестров и по умолчанию
включают только активные сущности:

- «Проекты»: название, ID и краткое описание, статус, ответственный, количество активных задач
  и этапов, срок и рассчитанный на дату экспорта риск; проекты сохраняют группировку из web;
- «Люди»: сотрудник, проекты, в которых он является ответственным или исполнителем, команды,
  недельная ёмкость и рабочий календарь. Email скрыт, пока не запрошен явно.

Названия статусов, дорожек расписания, категорий работ и типов отсутствий выводятся как
человекочитаемые заголовки, а не технические slug. PDF создаётся в альбомной ориентации,
с повторяющимися заголовками таблиц, увеличенным нижним полем под футер и пометкой
tagged PDF.

### Статический HTML

Один автономный HTML-файл строится из той же модели. Если разделы не указаны, включаются
все отчёты. В файле нет форм, кнопок редактирования, публикации и других мутаций.
Навигация реализована обычными ссылками внутри файла. Пользовательский Markdown
выводится как безопасный текст. Таблицы прокручиваются внутри контейнера, поэтому
узкая ширина экрана не растягивает всю страницу. Email по умолчанию скрыт.

### CSV

ZIP содержит отдельный UTF-8 CSV с BOM для каждой найденной repository schema, включая
`work-categories.csv`, а также аналитические таблицы `report-*.csv` из `ExportReportModel`.
Сырые массивы и вложенные значения по-прежнему кодируются JSON внутри ячейки.

### XLSX

Книга таблиц строится из той же модели отчётов. Это аналитический формат, а не выгрузка
сырых YAML-полей.

### Repository ZIP

Вариант без Git содержит рабочую копию как есть, кроме `.git`. Символические ссылки
сохраняются как ссылки и никогда не разыменовываются за пределы репозитория.

Вариант с Git добавляет переносимую `.git`-историю. Для worktree это новая локальная
копия истории, а не служебный `.git`-указатель на каталог GitPM. URL `origin`
намеренно удаляется: экспорт не должен переносить локальные пути или потенциальные
учётные данные. Рабочие файлы, включая незакоммиченные и untracked, берутся из
экспортируемой рабочей копии.

## Настройки

Общие параметры отрисованных форматов:

- область: весь портфель, проект, сотрудник или команда;
- дата «по состоянию на» и период;
- lifecycle: активные, архивные или все;
- состояние TimeEntry: активные, аннулированные или все;
- приватность: скрывать email, авторов и заметки;
- оформление: A4/Letter и компактный или подробный режим.

DOCX как отдельный формат не добавляется: модель общая, а публичный enum расширен
только на XLSX.

## CLI

```bash
gitpm export --format pdf --locale ru
gitpm export --format pdf --section projects --section people \
  --section project-details --section gantt
gitpm export --format html --section portfolio --section plan-fact --section workload
gitpm export --format csv
gitpm export --format xlsx --section plan-fact --section vacations
gitpm export --format repository
gitpm export --format repository --include-git
```

В worktree-режиме нужен `--draft <id>`. В direct-режиме используется выбранный
checkout. По умолчанию файл записывается в текущий каталог под сгенерированным именем.
`--output <path>` задаёт другой путь. Существующий файл не перезаписывается без
явного `--force`.

## HTTP

```text
GET /api/drafts/:draftId/export
  ?format=pdf|html|csv|xlsx|repository
  &locale=ru|en
  &sections=portfolio,project-plan,plan-fact,workload,vacations,person-profile,audit
  &scope=portfolio|project|person|team
  &project=<id>&person=<id>&team=<id>
  &as_of=YYYY-MM-DD&period_start=YYYY-MM-DD&period_finish=YYYY-MM-DD
  &lifecycle=active|archived|all
  &include_email=true|false
  &hide_personal_data=true|false
  &include_git=true|false
```

Прежние значения `projects`, `people`, `project-details` и `gantt` принимаются как
совместимые псевдонимы. Ответ — бинарное вложение с `Content-Disposition`,
`Content-Type` и `Cache-Control: no-store`. Неподдерживаемые параметры возвращают
стабильные `EXPORT_*` error codes. Невалидная структура repository не отрисовывается и
возвращает `EXPORT_REPOSITORY_INVALID`.
